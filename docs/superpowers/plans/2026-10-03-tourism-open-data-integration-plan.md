# BiteMap 觀光署開放資料整合計劃書

## 1. 文件目的

本文件說明如何把交通部觀光署開放資料整合進 BiteMap，先完成可展示、可驗證的 POC，再決定是否進入正式同步與推薦流程。

本文件同時保留資料整合設計與實作進度。第一階段預計使用前四個資料集：餐飲、景點、旅館民宿、旅遊服務站點。

目前已在 `tourism-open-data-poc` 分支完成第一個實作切片：四類資料匯入、資料庫外部資料層、公開查詢 API、管理員一鍵匯入，以及地圖獨立圖層展示。自有 BiteMap 店家仍與官方外部資料分開保存，後續再以匹配表整合評分與 Google 資訊。

## 2. 整合範圍

| 資料集 | 官方資料頁 | 在 BiteMap 的用途 | 預計同步頻率 |
| --- | --- | --- | --- |
| 餐飲－觀光資訊資料庫 | [data.gov.tw/7779](https://data.gov.tw/dataset/7779) | 提供官方餐廳候選資料，作為探索、地圖與行程規劃的外部資料來源 | 每日 |
| 景點－觀光資訊資料庫 | [data.gov.tw/7777](https://data.gov.tw/dataset/7777) | 作為旅遊目的地、附近餐廳與行程起點 | 每日 |
| 旅館民宿－觀光資訊資料庫 | [data.gov.tw/7780](https://data.gov.tw/dataset/7780) | 提供住宿與餐廳、景點的鄰近關係 | 每日 |
| 旅遊服務站點（借問站及旅遊服務中心） | [data.gov.tw/44055](https://data.gov.tw/dataset/44055) | 提供遊客諮詢、服務與旅途中繼點 | 每年 |

第一版只讀取官方資料，不直接覆蓋 BiteMap 管理員建立的店家資料，也不會對所有匯入資料自動呼叫 Google API。

## 3. 核心整合原則

### 3.1 官方資料與 BiteMap 主資料分離

目前 `restaurants` 是 BiteMap 自己管理的店家主資料，已經和菜單、照片、評論、約飯流程及 Google 查詢綁定。若把四個資料集直接寫進 `restaurants`，會產生以下問題：

- 大量官方資料會混入現有探索結果，影響目前的推薦與測試資料。
- 同一間店可能同時存在於官方資料與手動資料，難以判斷哪筆可以編輯。
- 官方資料更新時，可能覆蓋管理員手動修正的名稱、照片或營業資訊。
- 每筆官方店家都觸發 Google 查詢會增加 API 成本與不必要的效能負擔。

因此 POC 採用「外部資料層」：官方資料先進入獨立資料表，經過驗證、去重與管理員確認後，才可以被引用或轉成 BiteMap 的正式店家。

### 3.2 匯入、審核、發布分成三個狀態

1. **已匯入**：資料格式正確，保留在外部資料層。
2. **待審核**：可能與現有 BiteMap 店家重複，或需要管理員確認是否採用。
3. **已發布／已連結**：可以在旅遊模式、地圖或行程規劃中使用。

官方資料不等於已通過 BiteMap 編輯審核的資料；前台要清楚顯示資料來源與更新時間。

## 4. 建議資料模型

### 4.1 `tourism_source_places`

建立一張統一的外部地點表，讓四個資料集共用讀取與地圖 API。

建議欄位：

| 欄位 | 說明 |
| --- | --- |
| `id` | BiteMap 內部 UUID |
| `source_dataset` | `food`、`attraction`、`hotel`、`service_site` |
| `source_record_id` | 官方資料的原始識別碼，例如 RestaurantID、AttractionID |
| `name` | 正規化後的名稱 |
| `description` | 官方描述 |
| `address` | 正規化後地址 |
| `phone` | 電話 |
| `latitude`、`longitude` | 座標 |
| `location` | PostGIS Point，供距離與範圍查詢 |
| `category` | restaurant、attraction、hotel、service_site |
| `official_url` | 官方或店家網站 |
| `opening_hours` | 原始營業／服務時間的結構化結果或 JSON |
| `raw_payload` | 未改寫的官方欄位，保留追溯能力 |
| `source_updated_at` | 官方資料的更新時間 |
| `fetched_at` | BiteMap 實際抓取時間 |
| `content_hash` | 用於判斷資料是否真的變更 |
| `status` | active、inactive、invalid、pending_review、published |
| `validation_errors` | 欄位驗證錯誤摘要 |

建立唯一約束：

```text
(source_dataset, source_record_id)
```

這可確保同一份官方資料重跑匯入時只更新原資料，不會重複新增。

### 4.2 `tourism_place_links`

用來記錄外部資料與現有 BiteMap 店家的關係，不直接改寫兩邊資料。

建議欄位：

| 欄位 | 說明 |
| --- | --- |
| `tourism_place_id` | 外部資料 ID |
| `restaurant_id` | 對應的 BiteMap restaurant ID，可為空 |
| `match_method` | source_id、exact_name_address、geo_candidate、manual |
| `match_score` | 系統計算的候選分數 |
| `review_status` | pending、approved、rejected |
| `reviewed_by`、`reviewed_at` | 管理員審核資訊 |

同一筆外部資料可以先保持 `pending`，等管理員確認後才與 BiteMap 店家建立正式連結。

## 5. 資料匯入流程

```text
官方資料資源
    ↓
手動 CLI／後續排程下載
    ↓
保存原始回應與匯入批次資訊
    ↓
資料集 adapter 轉成統一格式
    ↓
欄位驗證、座標驗證、內容雜湊
    ↓
依 source_dataset + source_record_id upsert
    ↓
名稱／地址／座標候選比對
    ↓
待審核或自動建立外部資料
    ↓
旅遊模式、地圖與行程 API 讀取
```

### 5.1 Adapter 設計

每個資料集使用一個 adapter，負責處理欄位名稱差異與資料格式差異：

- `FoodDatasetAdapter`
- `AttractionDatasetAdapter`
- `HotelDatasetAdapter`
- `ServiceSiteDatasetAdapter`

Adapter 只做「轉換」，不負責決定是否發布。這樣官方欄位變動時，只需調整該資料集 adapter，不會影響地圖、探索或推薦邏輯。

### 5.2 正規化規則

- 名稱：去除前後空白、連續空白與常見標點差異，但保留顯示用原始名稱。
- 地址：統一全形／半形、空白、縣市與行政區格式，用於搜尋與比對。
- 電話：保存原始值，同時抽取可搜尋的數字形式。
- 座標：轉成數字並檢查台灣合理經緯度範圍；無座標資料列進入 `invalid`，不進入地圖。
- URL：驗證 HTTP／HTTPS 格式。
- 營業時間：先保留原始文字；只有格式穩定的資料才轉成可查詢的星期與時段。
- 空值：不把空字串當成有效資料，保留 `NULL` 並記錄必要欄位缺失。

### 5.3 匯入結果報告

每次匯入應記錄：

- 下載筆數
- 新增筆數
- 更新筆數
- 無變更筆數
- 停用筆數
- 無效筆數與錯誤原因
- 找到可能重複的筆數
- 待人工審核筆數
- 匯入開始／結束時間與來源 URL

POC 初期先以手動 CLI 執行，確認資料品質與查詢流程後，再考慮排程或背景工作。

## 6. 去重與人工審核

### 6.1 去重順序

1. 先用 `(source_dataset, source_record_id)` 判斷是否是同一筆官方資料。
2. 再以正規化名稱 + 地址判斷是否可能對應既有 BiteMap 店家。
3. 名稱相似但地址不同時，不自動合併。
4. 名稱不同但座標在小距離內時，只建立候選，不直接覆蓋。
5. 無法確定的資料維持 `pending_review`，交由管理員處理。

### 6.2 管理員審核動作

管理員介面新增「觀光資料」區塊，至少提供：

- 查看最近匯入批次與錯誤報告。
- 查看待審核候選，並對照官方名稱、地址、座標與 BiteMap 店家。
- 「連結到既有店家」：保留兩邊資料，只建立 link。
- 「建立為 BiteMap 店家」：複製必要欄位到 `restaurants`，來源標記為官方資料，之後仍由管理員維護。
- 「忽略候選」：不再重複提示，但保留官方資料。
- 查看資料來源與官方更新時間。

Google 自動搜尋只允許在管理員明確啟用、或店家被正式提升為 BiteMap 店家時執行；不對四個資料集的所有紀錄批量呼叫。

## 7. 前台如何使用

### 7.1 地圖

新增「旅遊資料」圖層，與目前 BiteMap 餐廳圖層分開：

- 餐廳：餐具圖示
- 景點：景點圖示
- 旅館民宿：住宿圖示
- 旅遊服務站：服務圖示

所有圖層共用 PostGIS 範圍查詢與距離排序，但 API 回應要包含 `category`、`source_dataset`、`source_updated_at`，前台才能顯示正確標籤。

### 7.2 探索與旅遊模式

第一版不要把官方資料直接混入目前「推薦排序」的餐廳結果。新增「旅遊模式」或明確的資料來源篩選：

- BiteMap 店家：可使用現有菜單、照片、約飯與評論功能。
- 觀光署資料：先提供官方地點資訊、距離與營業資訊。
- 已連結店家：可同時顯示官方資料與 BiteMap 內容，但要標示兩種資料來源。

這樣可以避免測試資料與外部資料互相污染，也不會讓使用者誤以為官方資料已經有 BiteMap 評論或再訪率。

### 7.3 行程與約飯流程

POC 示範流程：

1. 使用者選擇一個景點或旅遊服務站。
2. 系統用座標查詢附近餐廳、住宿與服務站。
3. 依距離、價格、料理分類與營業時間產生候選清單。
4. 使用者建立約飯，邀請朋友一起從候選餐廳投票。
5. 已有 BiteMap 店家可以進入現有聊天、投票與收藏流程；未連結的官方資料先以外部地點卡片呈現。

AI 若後續加入，只能根據已查詢到的候選資料做摘要與行程敘述，不得自行補造不存在的店家、評論、評分或營業時間。

## 9. 驗收條件

- 至少成功使用一個觀光署開放資料集；本 POC 目標為四個都能匯入。
- 同一資料集重跑匯入不產生重複資料。
- 官方資料的更新會反映在外部資料層，不會覆蓋管理員手動資料。
- 無效座標與缺少必要欄位的資料會被記錄並排除於地圖之外。
- 地圖能分辨四種資料類別，並能查詢附近地點。
- 前台能顯示資料來源與最後更新時間。
- 管理員能看到匯入統計與待審核候選。
- 既有手動餐廳、菜單、照片、評論、聊天與約飯流程不受影響。
- POC 能完成一條可展示的旅遊情境流程，而不是只有資料庫匯入。

## 10. 第一版明確不做的事

- 不把所有官方餐廳自動發布成 BiteMap 正式店家。
- 不對每一筆官方資料自動呼叫 Google Places API。
- 不在匯入階段自動產生評論、評分、再訪率或可信度分數。
- 不先做即時爬蟲；先使用官方提供的資料資源。
- 不在沒有實際查詢量前預先引入 Redis 快取；先用資料庫索引與批次匯入驗證效能。
- 不讓 AI 自行決定資料真偽或覆蓋官方／管理員資料。

## 11. 風險與處理方式

| 風險 | 處理方式 |
| --- | --- |
| 官方欄位或格式變動 | 每個資料集獨立 adapter，匯入前做 schema 與欄位驗證 |
| 同一地點有多筆資料 | 先依官方 ID 去重，再建立候選供管理員確認 |
| 官方資料不完整或過期 | 顯示來源更新時間，不把缺值補成推測值 |
| 大量匯入影響 API | 批次 upsert、資料庫索引，匯入與前台請求分離 |
| Google API 成本增加 | 只有管理員明確啟用時才查詢，外部資料預設不查 |
| 授權與來源追溯 | 保留來源資料集、來源 URL、原始 ID、官方更新時間與原始 payload |
| 外部資料污染現有功能 | 外部資料層與 `restaurants` 分離，發布前需經審核 |

## 12. 建議的第一個實作切片

第一個可交付切片建議只做「餐飲 + 景點」：

1. 建立外部資料表。
2. 匯入兩個資料集。
3. 提供範圍內的地圖查詢 API。
4. 在地圖以不同圖示顯示景點與官方餐廳。
5. 顯示來源與更新時間。
6. 用一個景點查詢附近餐廳，完成 POC 展示。

這個切片能先驗證最重要的資料流與使用情境；確認模型、查詢效能與 UX 後，再接旅館民宿與服務站，避免一開始同時處理四種欄位差異而難以除錯。
