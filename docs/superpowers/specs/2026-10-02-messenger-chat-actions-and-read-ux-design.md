# Messenger 風格聊天室操作與已讀 UX 設計

## 目標

將約飯群組聊天與私聊／好友聊的訊息操作調整為接近 Messenger 的互動方式，讓訊息方向、更多操作、回覆、收回、釘選與已讀狀態更容易理解，並且在重新整理、重連與多個聊天室視窗中保持一致。

## UI 行為

- 自己發送的訊息靠右排列，不顯示自己的頭像；他人訊息靠左排列並顯示頭像。
- 訊息氣泡保留伺服器時間排序。桌面與手機版都使用同一個排列規則。
- 每則訊息提供更多操作按鈕，使用垂直三點圖示；按鈕具備可讀的 aria-label。
- 更多選單提供「回覆」、「收回」、「釘選」三項操作。
- 「收回」只有作者在訊息建立後 2 分鐘內可以使用；收回後保留訊息紀錄，內容顯示「訊息已收回」。
- 「回覆」會在輸入框上方建立引用預覽，送出後保存被引用訊息 ID；引用訊息顯示作者、摘要與跳轉／定位入口，引用內容被收回時顯示「訊息已收回」。
- 「釘選」是聊天室層級狀態，聊天成員可以釘選或取消釘選訊息；釘選訊息會顯示釘選標記，聊天室上方顯示目前釘選入口與列表。
- 釘選支援同一聊天室多筆訊息；同一則訊息不可重複建立釘選紀錄。

## 已讀規則

- 每位聊天室成員維持一個伺服器端已讀游標，只能向較新的訊息前進。
- 聊天室開啟並完成歷史載入後，只有在使用者位於訊息列表底部或主動跳到底部時才更新已讀游標。
- 收到新訊息但使用者正在閱讀較早訊息時，不更新已讀游標，改顯示新訊息提示。
- 前端不因收到自己的 `conversation.read` 事件就把所有訊息標示為已讀；只在自己的最新相關訊息下方顯示已讀狀態。
- 已讀事件必須在後端成功更新游標後才透過 WebSocket 廣播，重連後以歷史／聊天室列表資料校正。

## 資料與事件

- `messages.reply_to_message_id` 使用自我外鍵保存引用關係；引用訊息刪除或收回時仍可解析為安全摘要。
- `message_pins` 使用關聯表保存聊天室釘選，包含訊息、釘選者與釘選時間；以訊息 ID 唯一，支援可逆 migration。
- 訊息 API 回應包含引用摘要、釘選狀態與目前使用者可執行的操作權限。
- WebSocket 新增 `message.reply`／帶 `reply_to_message_id` 的送訊息欄位、`message.pin`、`message.unpin`，並廣播 `message.pinned`、`message.unpinned` 與包含引用資訊的訊息事件。
- 回覆、釘選與收回都必須沿用現有 direct／meal 聊天權限與封鎖規則；同飯局封鎖不影響飯局群聊。

## 不在範圍

- 不加入圖片、檔案、貼圖、表情反應或語音訊息。
- 不改變好友關係、私訊限制、飯局成員資格或既有 WebSocket Redis 架構。

## 驗收

- 自己的訊息在右側且沒有頭像，他人訊息在左側且有頭像。
- 三點更多選單可正常開關，回覆、收回、釘選可保存並即時同步。
- 回覆與釘選在重新整理、重新連線及另一個聊天室頁面仍一致。
- 已讀不會因收到新訊息而錯誤前進；只有真正到底或主動跳到底部才更新。
- backend migration 可升級與降級，API／WebSocket 整合測試與 frontend typecheck、測試通過。
