# 約飯草稿、跨頁選店與飯局詳細頁 UX 設計

## 範圍與已確認決定

本設計延伸 Stage 7 既有約飯功能，解決三個問題：從餐廳發起後難以繼續挑選第 2、3 家店、約飯列表常駐管理面板造成視覺干擾，以及原生日期時間欄位不易操作。

- 從餐廳詳細頁發起約飯時，該店自動成為候選 1。
- 使用者可以保留未送出的約飯草稿，回到探索與餐廳詳細頁繼續選店。
- 候選餐廳只能在餐廳詳細頁加入，不在探索卡片提供快速加入按鈕。
- 一場公開投票約飯最多三家候選；只有一家候選時也能使用跨頁選店流程。
- 第一家餐廳選入時自動產生可編輯的飯局名稱。
- 約飯列表只負責瀏覽摘要；候選管理、投票、成員與發起人操作移到獨立飯局詳細頁。
- 正式成員才能看到票數與投票控制。未加入公開約飯者可看候選餐廳，但私人約飯在審核通過前不顯示候選內容。
- 時間設定改為快捷日期、快捷時段與自訂選項，不加入「現在」。

聊天室仍屬 Stage 8，本次只為未來在飯局詳細頁加入聊天室保留資訊架構位置，不實作聊天功能。

## 約飯草稿

### 保存範圍

草稿保存在目前瀏覽器分頁的 `sessionStorage`，固定使用帶版本的 key `bitemap.mealDraft.v1`。草稿包含：

- 公開／私人模式。
- 飯局名稱、名稱是否曾由使用者手動修改、簡介。
- 用餐日期與時間、加入截止分鐘數、人數上限。
- 選餐廳方式。
- 已選餐廳 ID 與顯示所需的最小摘要，最多三家。

草稿在同一分頁切換探索、地圖、餐廳詳細頁、約飯頁與重新整理時保留。建立成功、使用者確認放棄草稿或關閉分頁後清除。草稿已有任何輸入或候選餐廳時，按「放棄草稿」需先顯示確認提示。

讀取草稿時驗證版本、欄位型別、候選數量與重複 ID；無效或舊版本資料直接清除，不阻塞頁面。已下架或無法讀取的候選餐廳從草稿移除，並以可關閉提示告知使用者。

### 跨頁流程

1. 使用者在餐廳詳細頁點擊「發起約飯」。
2. 系統建立本地草稿，將目前餐廳放入候選 1，並開啟約飯建立介面。
3. 建立介面提供「繼續選店」；點擊後保存目前欄位並返回探索頁。
4. 探索、地圖與餐廳詳細頁在 Footer 上方顯示精簡草稿列：`約飯草稿・已選 1 / 3`，並提供「返回填寫」與「放棄」操作。
5. 使用者進入另一家餐廳詳細頁。公開投票草稿的主要操作改為「加入候選」；加入成功後留在目前餐廳頁，草稿列更新數量。
6. 達到三家後，其他餐廳顯示「候選已選滿」；已選餐廳顯示「已在約飯草稿」，兩者都不可重複加入。
7. 使用者可繼續瀏覽或點「返回填寫」回到建立介面送出。

若草稿為「先決定餐廳」，餐廳詳細頁操作使用「選為餐廳」；再次選擇其他店會取代原餐廳，不會建立第 2、3 家候選。私人約飯沿用目前已確認規則，不開放候選投票。

## 自動飯局名稱

第一家餐廳加入且名稱欄仍為空白、也未曾被手動修改時，自動填入：

```text
一起吃 {餐廳名稱}
```

例如「7-11 大中原」會產生「一起吃 7-11 大中原」。名稱仍可自由編輯。使用者一旦修改名稱，即標記 `titleTouched=true`；之後新增、移除或更換餐廳都不得覆蓋使用者文字。

若名稱尚未被手動修改：

- 更換第一家餐廳時，名稱同步更新。
- 移除第一家但仍有其他候選時，改用新的候選 1。
- 移除全部餐廳時，清空自動名稱。

送出 API 前仍以後端既有名稱長度與必填規則驗證，不依賴前端自動名稱取代驗證。

## 時間設定

建立介面不再使用單一 `datetime-local` 欄位，改為可快速選擇且仍能精確調整的兩段式控制。

### 日期

- 快捷選項：今天、明天、本週末、自訂。
- 點「本週末」後顯示本週六與本週日；若本週末已完全過去，改指向下一個週末。
- 點「自訂」後使用原生日期選擇器，只允許今天以後的日期。

### 時間

- 午餐：12:00。
- 下午茶：15:00。
- 晚餐：18:30。
- 宵夜：21:00。
- 自訂：使用原生時間選擇器。

今天已過去的快捷時段直接停用。日期與時間都選定後，在控制區上方顯示完整摘要，例如 `10 月 3 日（六）18:30`。系統不偷偷預選日期或時間；送出時缺少任一項，將焦點移到缺少的控制並顯示具體錯誤。

### 加入截止

公開約飯以 `5、10、15、20、30 分鐘前`按鈕取代滑桿，預設 15 分鐘。選定用餐時間後同步顯示實際截止時間，例如 `18:15 停止加入`。如果用餐時間過近，導致截止時間不晚於目前時間，建立介面需要求使用者改選較晚的用餐時間或較短的截止間隔，不送出無效資料。

私人約飯維持不設定加入截止時間。

## 約飯列表與詳細頁

### 約飯列表

`/meals` 不再自動把第一個可管理或可投票飯局的操作面板常駐在列表下方。每張卡只顯示飯局摘要、候選或已決定餐廳摘要、時間、人數與一個符合狀態的主要操作：

- 一般狀態：查看飯局。
- 發起人：管理飯局。
- 需要目前使用者投票：前往投票。
- 尚未加入且可加入：加入飯局。

點卡片或主要操作前往 `/meals/{mealId}`。多場約飯只增加卡片，不會在列表中插入大型候選、成員或投票面板。

### 飯局詳細頁

詳細頁使用單一內容層級，不把候選管理再包成與主卡片平行的大型白色卡片。

1. 頁首顯示飯局名稱、狀態、時間、人數與發起人。
2. 餐廳區使用同一份候選清單承接各狀態：
   - 尚未投票：候選餐廳清單。
   - 投票中：清單項目直接變成單選控制。
   - 已決定：突出最終餐廳，其餘候選降低視覺層級。
3. 成員區預設收合，只顯示頭像摘要與 `目前人數 / 上限`；發起人展開後才能管理成員。
4. 手機使用底部固定操作列；桌面使用內容右側或頁面底部操作區。
5. 發起人操作集中為新增候選、開始投票、確認結果與解除約飯；一般正式成員只顯示投票與退出約飯。

## 候選與投票可見性

- 未加入公開約飯者可查看候選餐廳名稱與基本資料，方便判斷是否加入，但不顯示票數、目前選擇或投票控制。
- `host` 與 `member` 正式成員在 `voting` 狀態可查看票數並投票；每人仍只有一票，改選會取代原票。
- `pending`、`rejected`、`left`、`removed` 與無 membership 的使用者不能查看票數或投票。
- 私人約飯只有發起人與審核通過的正式成員能查看候選內容；私人投票仍不實作。
- 候選回應的 `vote_count` 改為 `int | null`；未授權查看票數時後端回傳 `null`，不能只靠前端隱藏已回傳的票數。
- 前端可見性只改善體驗，候選私人資料、票數與投票端點仍需由後端依 membership 與飯局狀態授權。

## 錯誤與恢復

- `sessionStorage` 不可用時，建立表單仍可操作，但跨頁前提示草稿無法保存並阻止使用者誤以為資料會保留。
- 餐廳詳細資料讀取或草稿保存失敗時保留目前頁面，顯示可重試提示；建立完成後的正式候選 API 失敗時保留飯局與既有候選，不做部分資料回滾假象。
- 草稿達上限、餐廳重複、餐廳已下架或狀態不允許修改時提供明確原因，不靜默失敗。
- 飯局詳細頁不存在或使用者無權查看時，回到約飯列表並保留可理解的錯誤訊息。
- 建立成功後先清除草稿，再導向新飯局詳細頁，避免重新整理後重複建立。

## 實作邊界

- 草稿是前端暫存，不新增資料表，也不在建立完成前寫入約飯 API。
- 既有正式約飯、候選與投票資料模型維持不變；`vote_count` 回應型別調整時同步更新後端授權、OpenAPI 型別與測試。
- 建立頁、草稿列與餐廳詳細頁共用同一個具版本的草稿 store，避免各頁各自維護不一致狀態。
- 飯局詳細頁獨立負責候選、投票與成員資料；列表不再持有選中飯局的完整操作狀態。

## 測試與驗收

- 從餐廳詳細頁發起時自動加入候選 1，並在未手動改名時產生正確名稱。
- 手動修改名稱後，加入、移除與更換餐廳不覆蓋名稱。
- 草稿在探索、地圖、餐廳詳情、約飯建立頁與重新整理之間保留；建立成功、確認放棄與關閉分頁後清除。
- 公開投票草稿能加入三家不同已發布餐廳，重複與第四家都有明確狀態。
- 只有一家候選時也能返回探索、再次進入詳細頁並回到建立介面。
- 快捷日期、週末日期、過期時段、自訂日期時間與截止時間換算都有單元測試。
- 約飯列表有多場飯局時不渲染任何常駐管理面板；每張卡導向正確詳細頁。
- 未加入公開約飯者可見候選但不可見票數；正式成員可投票；私人待審核者不可見候選。
- 手機底部草稿列與飯局操作列不遮擋 Footer，桌面與手機皆完成鍵盤焦點、錯誤、空狀態與 reduced-motion 驗收。
- 完成後同步更新 `FUNCTIONAL_REQUIREMENTS.md`、`DEVELOPMENT_PLAN.md` 與必要 README 專案結構，並執行 formatter、lint、typecheck、相關前後端測試與 production build。
