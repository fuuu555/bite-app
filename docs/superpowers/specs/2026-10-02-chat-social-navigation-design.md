# 聊天室操作與社交導覽調整設計

日期：2026-10-02

## 目標

改善聊天室的訊息操作與可讀性，並將好友管理移到聊天室區域，同時保留約飯功能本身與約飯群組聊天室的既有流程。

## 明確不變的範圍

- 約飯分頁與約飯功能不調整。
- 約飯建立、加入、申請、投票、退出、解除、成團與成員權限維持現有行為。
- 約飯群組聊天室仍只服務該飯局的正式成員，不混入一對一聊天或好友名單。
- 圖片訊息仍不納入本次工作。

## 聊天室導覽

聊天室區域改為三個入口：

```text
聊天室
├── 聊天
├── 約飯聊天室
└── 好友管理
```

- `聊天`：合併原本的私聊與好友聊，所有一對一對話集中在這裡；列表可用好友／非好友狀態標示，但不再拆成兩個聊天分類。
- `約飯聊天室`：只列出使用者有權限進入的飯局群組聊天。
- `好友管理`：承接原個人頁面的好友列表、好友邀請、解除好友及陌生人私聊設定。
- 個人頁面的「好友」入口改為「美食地圖」，既有追蹤功能保留在美食地圖內。

## 訊息操作 UX

- 每則訊息保留三點操作 icon。
- 操作 icon 放在訊息泡泡旁邊，不放在訊息下方；自己的訊息仍靠右，icon 位於泡泡左側，他人訊息則依現有左側排列提供操作入口。
- 三點選單提供：
  - 回覆
  - 收回（只對符合權限與時間限制的自己的訊息顯示）
  - 釘選／取消釘選
- 回覆預覽必須清楚顯示原作者與原訊息摘要；長文字截斷但不得變成不可見或低對比文字。
- 釘選區使用清楚的固定區塊，顯示釘選訊息作者、摘要、釘選狀態與跳轉到原訊息的操作；不能只依靠小型 pin 標記傳達狀態。

## 頭像互動

約飯介面、約飯群組聊天室與一對一聊天中的他人頭像都可以點擊。點擊後顯示兩個操作：

1. 查看個人資料
2. 私聊

若對方拒絕陌生人私聊，私聊操作需呈現明確 disabled 狀態與原因；不能只在點擊後靜默失敗。好友或既有對話仍依既有後端 Policy 判定，前端不以隱藏按鈕取代權限檢查。

## 資料與同步原則

- 優先沿用現有好友、封鎖、私聊設定與聊天室 API，不重複建立好友資料。
- 聊天室分類與好友管理入口是前端導覽調整；除非現有 API 無法支援，否則不新增約飯資料模型。
- 頭像選單的個人資料與私聊操作沿用後端權限回應；禁用私聊時由後端拒絕並由 UI 呈現原因。
- 回覆、收回、釘選仍使用目前已完成的持久化資料與 WebSocket 同步。

## 驗收條件

- 約飯功能與約飯分頁行為未被改動。
- 聊天室可分別進入聊天、約飯聊天室、好友管理。
- 原私聊與好友聊的對話都能在「聊天」中查看，歷史不遺失。
- 好友管理不再出現在個人頁；個人頁改顯示美食地圖，追蹤仍可使用。
- 三點選單可操作回覆、收回、釘選／取消釘選，且訊息旁即可點擊。
- 回覆文字可讀、釘選內容清楚可辨識並可跳回原訊息。
- 約飯、約飯群聊及一對一聊天中的頭像都能開啟個人資料／私聊選單。
- 對方禁用私聊時，UI 明確顯示不可私聊原因。
- 桌面與手機寬度皆不會因操作選單或釘選區造成訊息內容被遮蔽。
