# Stage 8 WebSocket、約飯即時同步與群組聊天室設計

## 範圍與交付順序

Stage 8 分三批交付，避免把即時通訊、社交關係及跨功能封鎖同時改動：

1. 建立 WebSocket／Redis 基礎，將約飯同步從固定輪詢改為事件驅動，並完成約飯群組聊天室。
2. 實作追蹤、好友、陌生人私訊與好友聊天沿用原紀錄。
3. 實作封鎖及跨搜尋、推薦、個人頁、私訊、好友、追蹤與約飯的共用 Policy。

本規格只涵蓋第一批。聊天室先支援純文字訊息、歷史分頁、即時收發與斷線重連。圖片、已讀狀態、輸入中提示與訊息收回留待後續規格。封鎖雙方已在同一飯局時不改變既有席次，等後續產品規則另行設計。

## 架構

登入使用者在 `/api/v1/ws` 建立一條共用 WebSocket 連線，約飯列表、約飯詳情與聊天室透過訂閱命令共用連線。FastAPI 驗證既有 HttpOnly 使用者 Session Cookie 與允許的 `Origin`；驗證失敗時預設拒絕。Redis Pub/Sub 將已提交的事件傳遞到所有 API instance，本機測試可使用相同介面的記憶體事件匯流排。

PostgreSQL 是約飯與訊息的唯一持久資料來源。既有約飯修改仍走 REST，交易提交後才發布 `meal.updated`。事件只攜帶飯局 ID、事件種類及必要版本資訊，前端收到後以 REST 重新取得依目前使用者權限裁切的最新狀態，避免經 Redis 廣播私人欄位或不可見票數。

聊天訊息由 WebSocket 接收。後端重新檢查正式成員資格、內容及頻率，成功寫入 PostgreSQL 後才發布 `message.created`。Redis 或 WebSocket 暫時失效不會造成已確認訊息遺失；重新連線後由 REST 歷史端點補齊。

## 資料模型

### `conversations`

一列代表一個永久聊天室。第一批只建立 `meal` 類型並以 `meal_event_id` 唯一連到飯局；欄位設計允許後續加入直接私訊，但不提前實作私訊行為。

### `conversation_members`

記錄使用者加入及離開聊天室的時間，供聊天列表與歷史參與紀錄使用。飯局聊天室的目前讀寫權限不信任此表，而是每次以 `meal_memberships` 的 `host|member` 狀態判定，避免退出或被移除後仍能發言。

### `messages`

保存聊天室、發送者、純文字內容及建立時間。內容去除首尾空白後必須非空，最長 2,000 個 Unicode 字元。訊息 ID 作為前端去重依據；第一批不加入附件、已讀、輸入狀態或收回欄位。

Migration 必須可逆，並為既有飯局建立對應聊天室，讓 Stage 7 已存在資料可直接使用。

## REST 與 WebSocket 契約

- `GET /api/v1/meals/{meal_id}/messages?cursor=&limit=`：正式成員讀取訊息，使用穩定游標向前分頁。
- `GET /api/v1/conversations?kind=meal`：列出目前使用者可進入的有效飯局聊天室及最新訊息摘要。
- `WS /api/v1/ws`：共用的驗證連線，不列入 OpenAPI 產生型別，前後端以明確事件型別維護契約。

客戶端命令包含 `subscribe`、`unsubscribe`、`message.send` 與 `ping`；伺服器事件包含 `ready`、`subscribed`、`meal.updated`、`message.created`、`ack`、`error` 與 `pong`。所有命令具有 `request_id`，讓前端配對成功或失敗結果。無效 JSON、未知事件、過長訊息及超過頻率限制都回傳安全錯誤，不暴露內部例外。

公開飯局的登入使用者可訂閱不含敏感資料的狀態失效事件。私人飯局只有發起人、正式成員及待審核申請者能訂閱與自身關係相關的狀態更新；只有 `host|member` 能訂閱聊天室、讀取歷史或發送訊息。退出、被移除或飯局解除後，伺服器立即撤銷聊天室訂閱及後續讀寫權限。

## 前端流程

使用者版面提供單一 client-side WebSocket Provider，按目前頁面訂閱需要的飯局。約飯列表及詳情收到 `meal.updated` 後重新讀取 REST；移除既有 10 秒及 3 秒固定輪詢，保留頁面重新取得焦點時的補資料作為斷線保護。

約飯詳情只對正式成員顯示聊天室。訊息依 ID 去重，首次載入顯示最新一頁，向上操作載入更舊訊息。新加入的正式成員可以查看整場飯局的完整歷史。發送失敗時保留輸入內容並允許手動重試，不建立可能重複送出的瀏覽器離線佇列。

`/chat` 保留「私訊／好友／約飯」分類，第一批啟用約飯聊天室列表；私訊與好友顯示明確的後續開放狀態，不建立假資料。

## 連線與錯誤處理

客戶端斷線後使用有上限的指數退避與隨機抖動重新連線。重連成功會恢復目前訂閱，並以 REST 更新畫面與補齊訊息。心跳用來清除失效連線；認證過期、來源不允許及授權失敗皆採 fail-closed。

訊息保存成功但即時發布失敗時，API 記錄可追蹤錯誤，使用者重連後仍能從歷史端點取得訊息。約飯資料提交失敗時不發布事件。事件內容不包含 Session Token、私人個人資料或非成員不可見票數。

## 測試與完成條件

- Alembic upgrade／downgrade 可逆，既有飯局都有唯一聊天室。
- WebSocket Session、`Origin`、訂閱及訊息命令都有成功與拒絕測試。
- 公開觀察者、私人待審核者與正式成員只收到各自允許的事件。
- 非成員不能讀取或發送訊息；退出、被移除或解除飯局後，既有連線立即失去聊天權限。
- 訊息先持久化再發布，重新連線可用 REST 補齊，分頁順序穩定且前端不重複顯示。
- 約飯加入、退出、審核、移除、候選、投票、結算與解除都會在提交後發布更新事件。
- 前端不再使用固定輪詢，連線、重連、錯誤、空白及載入狀態都有測試。
- Redis 跨 instance 整合、後端單元／整合測試、前端測試、OpenAPI Client、lint、typecheck、formatter、production build 與主要 E2E 流程通過。
