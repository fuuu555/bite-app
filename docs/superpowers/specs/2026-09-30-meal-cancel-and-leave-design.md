# 約飯解除與退出設計

## 目標

讓約飯發起人可以安全解除尚未完成的飯局，並讓已加入的普通成員可以主動退出。資料採軟狀態更新，保留成員與飯局紀錄，避免破壞後續稽核與時間線。

## 行為規則

- 發起人可在 `open`、`voting` 或 `decided` 狀態解除約飯。
- 解除約飯會將飯局狀態改為 `cancelled`，不刪除飯局、候選餐廳、投票或成員資料。
- 只有 `completed` 不允許解除；後端必須拒絕繞過前端的請求。
- 普通正式成員可在尚未完成的有效飯局退出；私人約飯的 `pending` 申請者也可撤回申請。
- 發起人不能使用退出操作，只能解除約飯。
- 退出後成員狀態改為 `left`，立即失去投票與後續聊天室權限；既有資料保留。
- 已取消飯局不再出現在公開或我的有效列表。

## API 與資料流

- 新增發起人專用 `POST /api/v1/meals/{meal_id}/cancel`。
- 沿用既有 `POST /api/v1/meals/{meal_id}/leave`，擴大到有效非發起人飯局，不由前端自行判斷權限。
- API 回傳完整最新飯局狀態，讓前端可即時更新列表。
- 取消與退出都使用後端服務層驗證角色、目前狀態及成員狀態。

## UI

- 發起人顯示「解除約飯」按鈕，點擊後先顯示確認提示，避免誤觸。
- 普通成員顯示「退出約飯」按鈕；私人申請中的使用者顯示同一操作入口並標明撤回申請。
- 投票中與已決定但尚未完成的飯局仍允許成員退出；退出後前端資格會立即失效，已完成或已取消的飯局不顯示退出操作。
- 操作成功後以既有回饋訊息更新列表，不新增重複卡片或隱藏式權限判斷。

## 驗證

- 後端測試涵蓋：發起人可取消、非發起人不可取消、已決定／完成不可取消、成員退出、發起人不可退出、退出後無法投票。
- 前端 typecheck、lint、測試與 production build 必須通過。
- migration 不需要新增欄位，沿用既有 `cancelled`／`left` 狀態。
